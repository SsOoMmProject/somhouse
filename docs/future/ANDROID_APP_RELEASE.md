# Android 앱 출시 패키지 (설계 · 2026-11-21 기준)

**상태: 설계만 있다.** 이 맥에는 JDK와 Android SDK가 없어 앱을 빌드하거나 실기기에서 돌려 보지 않았다. 검증하지 못한 네이티브 코드를 넣어 두면 나중에 오히려 짐이 되므로, 지금은 무엇을 어떤 순서로 해야 하는지만 고정한다. 저장 구조는 [#31 앱 전환 설계](../APP_ARCHITECTURE_PLAN.md)를 따른다.

## 앱이어야만 되는 것

웹으로 이미 되는 기능은 앱으로 옮겨도 코드를 그대로 쓴다. 앱을 만드는 이유는 아래 다섯 가지다.

| 기능 | 사용자에게 달라지는 점 | 필요한 Android 기능 |
|---|---|---|
| 홈 화면 위젯 | 앱을 열지 않고 마지막 수유·수면·기저귀 확인, 한 번 탭으로 기록 | App Widget |
| 정확한 알림 | 캘린더를 거치지 않는 수유·낮잠·투약 간격 알림 | 로컬 알림, 정확한 알람 권한 |
| 휴대폰 캘린더에 바로 쓰기 | 삼성 캘린더 35분 지연 해결 (#31에 측정 기록) | CalendarContract |
| 백그라운드 음성 가져오기 | 앱을 안 열어도 Nest·Gemini 입력 반영 (약 15분, 보장 안 됨) | WorkManager |
| 공유로 받기 | 병원 예약 문자·사진을 솜하우스로 공유해 일정으로 | Share Target |

## 구조

- **Capacitor**로 지금의 웹 코드를 감싼다. 웹과 앱이 같은 화면 코드를 쓴다.
- 저장은 `core/sync-core.js` (동기화 코어 PR)를 쓴다. 기기의 로컬 사본 + 가족 Google 시트의 추가 전용 로그.
- 로그인은 휴대폰의 Google 로그인. 서버 비밀값을 앱에 넣지 않는다.
- 기능 스위치(`features.js`)를 그대로 쓴다. 앱 빌드별로 켜는 기능을 다르게 할 수 있다.

## 출시 관문 (순서대로)

| # | 관문 | 필요한 것 | 걸리는 시간 |
|---|---|---|---|
| 1 | 개인정보 | 동의·내 데이터 센터 PR 적용, 처리방침 갱신, 법률 검토 | 사용자 결정 |
| 2 | 소유 도메인 | `github.io`·`ts.net`은 소유 확인 불가. 도메인 구입, 소개·방침 페이지 이전 | 1일 |
| 3 | Google OAuth 검증 | Calendar·Tasks 민감 범위 심사, 시연 영상, 범위별 사유. **지금 쓰지 않는 기능의 권한은 미리 요청할 수 없다** | 보통 수 주 |
| 4 | Play 개발자 계정 | 등록비 25달러, 본인 인증 | 수일 |
| 5 | 비공개 테스트 | 2023-11-13 이후 만든 **개인 계정은 테스터 12명이 14일 연속** 참여해야 프로덕션 신청 가능 | 3주 전후 |
| 6 | Play 건강 앱 신고 | Health apps 선언서, 개인정보처리방침, 앱 설명에 “의료기기가 아니며 진단·치료·예방을 하지 않는다” 고지 | 심사 포함 수일 |
| 7 | 데이터 보안 양식 | 수집 항목, 건강 정보, AI 회사 전송을 실제와 같게 신고 | 1일 |

iPhone은 지금 범위가 아니다. 나중에 낼 때는 App Store 심사 지침 5.1.2(i)에 따라 **외부 AI로 개인정보를 보내기 전에 무엇을 누구에게 보내는지 밝히고 허락**을 받아야 한다. 동의·내 데이터 센터의 AI 전송 동의가 이 요건의 바탕이 된다.

## 적용할 때 사용자가 해 줄 일

1. Android Studio 설치(JDK·SDK 포함)
2. Galaxy 휴대폰 USB 디버깅 켜기
3. 도메인과 Play 개발자 계정 결정
4. 테스터 12명 모으기 (가족·지인)
