# 기본 캘린더 정정 반영 설계 — 2026-11-17

웹에서 정정한 수유(예: `뷰유` → 분유 10ml)를 사용자의 **기본 캘린더 원래 일정**에도 반영하는 기능의 설계입니다. 구현은 `feature/calendar-writeback` 브랜치의 PR로 준비돼 있으며 **병합하지 않고 보관**합니다. Google 계정을 다시 연결할 때(Testing 토큰 만료 예상 2026-11-23경) 병합·배포하고 쓰기 권한을 받습니다.

## 현재 상태 (구현 전)

- 기본 캘린더 권한은 읽기(`calendar.events.owned.readonly`)뿐입니다. 웹 정정은 솜하우스 기록과 원본 시트에만 남습니다.
- 데이터 흐름은 **캘린더 → 웹** 한 방향입니다. 캘린더 수정과 웹 수정은 항목별로 합칩니다(`calendar_records.merge_edit`).
- 앱이 만든 "솜하우스 수유" 캘린더 일정에는 `extendedProperties.private.somhouseProjection = "1"`이 붙어 있고, 수집할 때 무시합니다.
- 따라서 지금은 웹 ↔ 캘린더 루프가 생길 수 없습니다.

## 위험

양방향이 되면 아래 순환이 생길 수 있습니다.

캘린더 입력 → 웹 수집 → 웹 정정 → 캘린더 수정 → 웹 재수집 → 다시 캘린더 수정 → …

솜하우스가 쓴 변경을 다시 "새 사용자 변경"으로 받아들이거나, 양쪽 값이 정규화 차이로 끝없이 달라 보이면 무한 반복이 됩니다. **정정을 바로 캘린더에 쓰면 안 됩니다.**

## 대책 (1~6 모두 필수)

| # | 대책 | 구현 방법 | 막는 것 |
|---|---|---|---|
| 1 | **내 변경 표시** | 솜하우스가 일정을 고칠 때 `extendedProperties.private.somhouseWrite`에 쓴 내용(제목·시작·설명)의 SHA-256 지문을 함께 저장합니다. 수집할 때 현재 내용의 지문이 이 값과 같으면 솜하우스가 쓴 그대로이므로 새 변경으로 취급하지 않습니다. | 메아리 |
| 2 | **같으면 쓰지 않기** | 쓸 제목을 만든 뒤 `calendar_feeding`으로 다시 해석해, 결과가 웹 기록(시각·양·종류)과 같은지 확인합니다. 이미 같으면 쓰지 않습니다. 해석 결과가 다르면 쓰지 않고 확인 필요로 보냅니다. | 같은 값 반복 쓰기, 정규화 차이로 인한 영구 불일치 |
| 3 | **버튼으로만 반영** | 웹에서 정정해도 자동으로 쓰지 않습니다. 캘린더에서 온 기록에만 **캘린더에도 반영** 버튼을 보여 주고, 누를 때 한 번 대기열에 넣습니다. | 연속 수정 중 핑퐁 |
| 4 | **동시 수정 감지** | 수집할 때 받은 일정의 `etag`를 보관하고, 쓸 때 `If-Match`로 보냅니다. 412(그사이 캘린더에서 수정됨)면 덮어쓰지 않고 확인 필요("캘린더가 먼저 바뀌었어요")로 넘깁니다. | 서로 덮어쓰기 |
| 5 | **횟수 제한(차단기)** | 일정마다 솜하우스가 쓴 횟수와 시각을 기록합니다. 24시간에 3회를 넘으면 그 일정의 반영을 멈추고 확인 필요로 넘깁니다. 관리자 해제 전까지 다시 쓰지 않습니다. | 1·2가 뚫린 경우의 무한 반복 |
| 6 | **원문 보존** | 제목을 고칠 때 원래 제목을 일정 설명 맨 위 `음성 원문: …` 줄에 남깁니다(이미 있으면 유지). 원본 시트에도 반영 이벤트(`calendar-writeback`)를 기록합니다. 사용자가 쓴 기존 설명은 지우지 않습니다. | 정보 손실 |

### 반영 대상 제한

- `google_calendar_inputs`에 있는(솜하우스가 수집한) 일정만 고칩니다. 임의 일정은 고치지 않습니다.
- 수정하는 필드는 `summary`와 `description`뿐입니다. 시작 시각·참석자·알림은 건드리지 않습니다.
- 반복 일정, 종일 일정, 다른 사람이 만든 일정은 버튼을 보여 주지 않습니다.

### 쓸 제목 형식

`분유 10ml`, `모유 15분`처럼 종류와 양만 씁니다. 기존 해석 규칙이 그대로 읽을 수 있는 형식이어야 하며(대책 2), 종류가 `기타`면 `수유 10ml`로 씁니다.

## 권한과 재연결

- 필요한 범위: `https://www.googleapis.com/auth/calendar.events.owned`(소유한 캘린더 일정 읽기·쓰기). 기존 `calendar.events.owned.readonly`를 대체합니다.
- 범위가 넓어지므로, 코드에서 위 "반영 대상 제한"을 지키고 테스트로 확인합니다.
- 휴대폰의 **Google 다시 연결** 또는 `scripts/connect_google_records.py --calendar`로 재연결해 새 토큰을 받습니다. 기존 `binding`·리소스 ID는 유지되는지 확인합니다.
- 쓰기 권한이 없는 토큰이면 버튼을 숨기고 기존 동작(읽기 전용)으로 남습니다.

## 배포 전 검증 (가짜 캘린더로)

1. 캘린더 입력 → 웹 정정 → 버튼 → 캘린더 반영 → 다시 수집: **추가 쓰기 0회**, 확인 필요 0건.
2. 반영 직후 사용자가 캘린더에서 같은 일정을 다시 고침: 412 처리, 덮어쓰지 않고 확인 필요.
3. 지문을 일부러 깨뜨려 루프를 만듦: 3회에서 차단기가 멈춤.
4. 원래 설명이 있는 일정: 설명 보존, `음성 원문` 줄 1회만 추가.
5. 다른 일정·반복 일정·종일 일정: 쓰기 요청 0회.
6. 읽기 전용 토큰: 버튼 없음, 쓰기 요청 0회.

실제 계정에서는 재연결 후 시험용 일정 1건으로만 확인합니다.

## 구현 위치 (PR 보관 중)

| 대책 | 코드 |
|---|---|
| 1 | `content_fingerprint`, `CalendarRecords.record`의 `somhouseWrite` 메아리 처리 |
| 2 | `writeback_check`의 재해석 비교와 마지막으로 본 캘린더 제목 비교 |
| 3 | `POST /api/calendar-writeback`, 기록 목록의 **캘린더에도 반영** 버튼(확인창 후 요청) |
| 4 | 수집 때 저장한 `google_calendar_inputs.etag`와 GET 결과 비교, PATCH `If-Match`, 412 처리 |
| 5 | `google_calendar_writes`, `WRITE_LIMIT = 3` / 24시간, 요청 시와 전송 시 모두 검사 |
| 6 | `with_original`, 원본 시트 `calendar-writeback` 이벤트 |

권한은 `scripts/connect_google_records.py`가 재연결 때 `calendar.events.owned`를 요청하고, Google이 실제로 허락한 경우에만 설정에 `calendar_write: true`를 저장합니다. 이 값이 없으면 버튼이 보이지 않고 서버도 요청을 거절합니다.

### 배포 순서 (2026-11-19 갱신: 휴대폰 재연결)

1. 이 PR을 병합하고 운영 폴더를 갱신한 뒤 서버를 재시작합니다. 아직 `calendar_write`가 없으므로 동작은 바뀌지 않습니다.
2. 휴대폰 솜하우스 홈 맨 아래 연동 줄(문제가 있으면 맨 위 경고)의 **Google 다시 연결**을 누르고 모든 권한에 체크해 승인합니다. 서버는 Google이 실제로 허락한 범위에 `calendar.events.owned`가 있을 때만 `calendar_write: true`를 저장하고, 새 권한으로 기본 캘린더·출력 캘린더·Tasks·시트를 읽어 본 뒤에만 교체합니다. 서버 재시작은 필요 없습니다. (맥의 `scripts/connect_google_records.py --calendar`도 계속 쓸 수 있습니다.)
3. `google-status`와 웹에서 캘린더 입력 수유 카드에 **캘린더에도 반영** 버튼이 보이는지 확인합니다.
4. 시험 일정 1건으로 반영 → 재수집 → 추가 쓰기 0회를 확인합니다.
